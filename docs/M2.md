# M2：函数识别与初始控制流图构建

状态：本地实现与固定样本自动测试完成。整理日期：2026-11-18。

本文记录第二阶段（M2）的实现过程、阶段依赖、接口、产物格式、地址与边的约定，以及当前样本上的验证结果和限制。M1 的历史与产物契约仍以 [M1.md](M1.md) 为准，本文不重写 M1。

## 1. 阶段目标与范围

M2 在 M1 的 `BinaryInfo` 基础上完成两项工作：

1. 识别函数入口，并给出函数与恢复代码块的对应关系；
2. 恢复可执行区域内的基本块、块内机器指令、直接/间接控制转移及其初始边关系。

输出为 `functions.json` 和 `cfg.json` 两个绑定输入 ELF 的 JSON 产物，地址统一使用 ELF 虚拟地址（VA）。M2 不消费 M1 内部的 CLE/angr 运行时对象，而是使用独立数据模型作为阶段间契约。

本阶段只构建“初始”控制流图，不等同于完整、精确的过程间分析：

- 不求解完整的间接调用目标，不进行跨过程指针分析；
- 不生成 VEX facts，不划分对象内存块，不做 SSA；
- 不执行程序，不产生运行期值；
- 调用续点、返回边和地址取用（address-taken，AT）候选都保留来源与不确定性标记，不能直接当作已证明的指针事实。

## 2. 与 M1 的依赖和一致性检查

M2 的输入是 M1 的 `BinaryInfo`。`build_cfg(info)` 在恢复 CFG 前检查：

| 检查项 | 要求 |
| --- | --- |
| 数据契约 | `schema_version == 2` 且 `address_space == elf-va` |
| 架构 | `arch` 为 `AMD64` 或 `X86` |
| 位宽/字节序 | 位宽与架构匹配，字节序为小端 |
| 入口与基址 | `mapped_entry == entry + load_bias` |
| 加载策略 | `auto_load_libs == False`，`loader_backend == "cle"` |
| 加载器版本 | `loader_version` 与当前安装的 CLE 版本一致 |
| 二进制身份 | 重新读取 `info.path` 的字节，SHA256 必须等于 `info.sha256` |
| 实际加载结果 | 私有 `angr.Project` 的架构、`linked_base`、`mapped_base`、`mapped_entry` 与 M1 一致 |

任一项不满足都会抛出 `CFGError`（`ValueError` 的子类），不生成半成品。M1 schema 1 的旧产物需要重新生成。

M2 重新读取同一个 ELF 字节快照，并用 `BytesIO` 建立私有的 `angr.Project`。因此输入文件可以搬家，但内容必须保持同一 SHA256；M1 记录的加载策略和映射基址不能与当前实现冲突。M1 的 `load_elf()` 返回 `BinaryInfo`，M2 的 `build_cfg()` 返回 `CFGResult`，两者之间不传递 angr/CLE 对象。

`run_m2()` 有两种入口行为：

- 不指定 `m1_path`：先在本进程执行 M1，再执行 M2；
- 指定 `m1_path`：读取已有的 `binary.json`，不重跑 M1；若命令行同时给出 `mapped_base`，必须与产物一致。读取后会以当前输入路径替换 M1 记录的路径，再由 `build_cfg()` 校验 SHA256 和加载结果。输入搬迁但字节相同是允许的。

## 3. 实现过程

1. **抽取通用 JSON 发布逻辑。** 将 M1 原有的“临时文件写入 + 原子替换”抽到 [src/bpa/artifacts.py](../src/bpa/artifacts.py)，继续拒绝输出路径解析到输入 ELF，或输出与输入是同一硬链接/符号链接的情况。
2. **建立 M2 独立模型。** 在 [src/bpa/model/cfg.py](../src/bpa/model/cfg.py) 定义不可变数据类：`Instruction`、`BasicBlock`、`Edge`、`Transfer`、`ATEvidence`、`Function`、`CFGResult`，只保存基本类型，支持稳定的 JSON 导出。
3. **恢复函数与图。** 在 [src/bpa/cfg/builder.py](../src/bpa/cfg/builder.py) 校验 M1 契约，重建私有项目，将 M1 中位于可执行区域内的已定义函数符号作为额外入口，限定可执行区域后运行 `CFGFast`。
4. **整理块、边与转移。** 用 CFG 图节点和 angr 的块解码得到基本块与机器指令；结合 M1 的导入表把外部目标标为符号名；丢弃未知的 `UnresolvableCallTarget` 占位节点；再按块最后一条指令汇总直接目标、间接目标、续点、外部目标和未解析状态。
5. **收集 AT 候选。** 从非直接控制转移指令的立即数、可恢复的 LEA 地址以及全局初始内存中的机器字收集候选，只保留命中已恢复函数入口的值，并记录来源地址。
6. **接入流水线与 CLI。** [src/bpa/pipeline.py](../src/bpa/pipeline.py) 提供 `run_m2()`，统一生成 M1 输入记录和 M2 两个产物；[src/bpa/__main__.py](../src/bpa/__main__.py) 增加 `--stage m2` 与 `--m1`，默认 `--stage m1` 的 JSON 文件输出行为不变。
7. **补充测试。** [tests/test_cfg.py](../tests/test_cfg.py) 只使用现有 `test_64`/`test_32`，覆盖函数与代码范围、图和指令完整性、独立线性反汇编核对、未解析调用、AT 证据、M1 校验、导出确定性及 CLI 复用 M1。

核心处理顺序为：

```text
M1 BinaryInfo
  → 校验 schema/架构/加载策略/入口与基址
  → 重新读取同一 SHA256 的 ELF，建立私有 angr.Project
  → 符号入口 + 可执行区域 + CFGFast
  → 函数、基本块、机器指令、边和转移
  → AT 候选及证据
  → CFGResult
  → functions.json / cfg.json
```

## 5. 接口

### 5.1 Python 接口

```python
from bpa.loader import load_elf
from bpa.cfg import CFGError, build_cfg
from bpa.pipeline import run_m2

info = load_elf("tests/fixtures/binaries/test_64")
result = build_cfg(info)                 # 返回 CFGResult

result.functions_document()              # functions.json 的字典
result.cfg_document()                    # cfg.json 的字典

run_m2("tests/fixtures/binaries/test_64", "outputs/test_64")
run_m2("tests/fixtures/binaries/test_64", "outputs/test_64",
       m1_path="outputs/test_64/m1/binary.json")
```

- `build_cfg(info: BinaryInfo) -> CFGResult`：只接受已校验的 M1 模型，失败抛出 `CFGError`。
- `run_m2(binary, output, *, m1_path=None, mapped_base=None) -> CFGResult`：`output` 是任务目录；生成 `m1/binary.json`（需要时）和 `m2/functions.json`、`m2/cfg.json`。
- `--mapped-base` 只应在 PIE 等需要显式基址时使用；与已有 M1 产物冲突会被拒绝。

### 5.2 命令行

```bash
# 直接执行 M1→M2，-o 是任务目录
PYTHONPATH=src uv run --locked python -m bpa \
  tests/fixtures/binaries/test_64 --stage m2 -o outputs/test_64

# 复用已有 M1 产物，不重跑 M1
PYTHONPATH=src uv run --locked python -m bpa \
  tests/fixtures/binaries/test_64 --stage m2 \
  --m1 outputs/test_64/m1/binary.json -o outputs/test_64

# M1 行为保持不变：-o 仍表示单个 JSON 文件
PYTHONPATH=src uv run --locked python -m bpa \
  tests/fixtures/binaries/test_64 -o outputs/test_64/m1/binary.json
```

`--stage` 默认为 `m1`。`--stage m2` 必须提供 `-o` 目录；`--m1` 只能与 `--stage m2` 一起使用。M2 成功后在标准输出打印产物目录和主要统计。

## 6. 产物与字段

### 6.1 目录布局

```text
outputs/<样本名>/
├── m1/binary.json          # M1 输入记录（schema 2）
└── m2/
    ├── functions.json      # 函数与 AT 证据（schema 1）
    └── cfg.json            # 块、边、转移和诊断（schema 1）
```

两个 M2 文件共享同一组元数据：

| 字段 | 含义 |
| --- | --- |
| `schema_version` | M2 产物版本，当前为 `1` |
| `stage` | `"M2"` |
| `address_space` | `"elf-va"`，所有地址为原始 ELF VA |
| `binary_path` | 本次读取的 ELF 路径 |
| `binary_sha256` | 绑定的 ELF SHA256 |
| `arch`、`bits`、`entry` | 架构、位宽和 ELF 入口 |
| `backend`、`backend_version` | `angr.CFGFast` 及 angr 版本 |
| `options` | CFGFast 选项及函数入口来源说明 |
| `kind` | `"functions"` 或 `"cfg"` |

`options` 记录 `normalize=True`、`resolve_indirect_jumps=True`、`detect_tail_calls=False`，以及“M1 已定义函数符号作为额外入口”。恢复范围限定在 M1 记录的可执行区域。

### 6.2 functions.json

`functions` 按入口地址排序，每一项包含：

| 字段 | 含义 |
| --- | --- |
| `entry` | 函数入口（ELF VA） |
| `name` | CFGFast 采用的函数名 |
| `aliases` | 同入口的其他 M1 符号名 |
| `source` | `elf-symbol`、`plt` 或 `cfgfast` |
| `symbol_end` | M1 符号带正大小时的结束地址，否则为 `null` |
| `blocks` | 归属于该函数的已恢复块入口 |
| `code_ranges` | 由归属块合并出的左闭右开代码区间 |
| `is_plt` | 入口是否命中 M1 的 PLT 记录 |
| `address_taken` | 是否收集到 AT 候选证据 |
| `at_evidence` | `source` + `address` 的证据列表 |

`source` 的优先级为：命中 M1 PLT 记录则记 `plt`；入口有 M1 符号名则记 `elf-symbol`；其余由 CFGFast 发现的函数记 `cfgfast`。外部 simprocedure 不作为真实函数导出。

`code_ranges` 只来自实际恢复并归属到该函数的块。实现不假定函数代码连续，也不用“下一个函数入口”推算未知边界；`symbol_end` 与 `code_ranges` 是两类独立信息。

### 6.3 cfg.json

| 字段 | 含义 |
| --- | --- |
| `blocks` | 基本块，含地址、大小、归属函数入口、块内机器指令、`jumpkind` |
| `edges` | 初始图边，含源/目标、边类型、原始 `jumpkind`、来源标记、外部符号 |
| `transfers` | 按块最后一条指令汇总的直接/间接控制转移 |
| `unresolved_transfers` | 所有状态为 `unresolved` 的间接转移地址（不只调用） |
| `diagnostics` | 无归属块、反汇编不完整等诊断 |
| `statistics` | 函数、块、边、调用、间接调用、未解析调用和 AT 函数计数 |

每个基本块的 `instructions` 按地址连续排列，最后一条通常决定该块的转移类型。块可能没有归属函数：这类块仍保留在 `blocks` 中，并在 `diagnostics` 记录，不伪造所有者。

`statistics` 中的 `calls` 统计所有 `kind == "call"` 的转移；`indirect_calls` 统计其中机器指令为间接形式的调用；`unresolved_indirect_calls` 再限定为未解析者；`at_functions` 是带 AT 候选的函数数。这些计数包含启动代码、运行库辅助代码和 PLT，不等于源码函数数量。

### 6.4 边与转移的约定

`Edge.kind` 与 `Edge.provenance` 的对应关系：

| `kind` | 含义 | 常见 `provenance` |
| --- | --- | --- |
| `call` | 调用；外部目标用 `target=null` 和 `external_symbol` 表示 | `machine-cfgfast` 或 `cfgfast-indirect` |
| `return` | CFGFast 推断的返回边 | `cfgfast-return` |
| `fake_return` | 调用后的续点假设 | `assumed-return` |
| `jump` | 直接或间接跳转 | `machine-cfgfast` 或 `cfgfast-indirect` |
| `branch` | 条件分支等非顺序后继 | `machine-cfgfast` |
| `fallthrough` | 顺序落入下一块 | `machine-cfgfast` |
| `other` | 其他 `jumpkind` | `machine-cfgfast` |

必须区分以下两类“看起来像返回”的信息：

- `fake_return` / `provenance=assumed-return` 只是“调用会继续到某处”的建模假设，用于保留调用后的控制流，不是已经求出的过程间返回或指针目标；
- `return` / `provenance=cfgfast-return` 是 CFGFast 的返回边推断，也不是已经完成的过程间指针求解。

未知的 `UnresolvableCallTarget` 占位节点不会导出成真实函数或真实目标。外部导入目标不创建伪函数，只在边上保留 `external_symbol`。

`Transfer` 是面向分析的逐块转移摘要，字段包括：转移指令地址、所属块、块归属函数、`kind`、`indirect`、直接目标、内部目标集合、外部目标、调用续点、`status`、`target_source`。

- 直接调用/跳转从机器指令立即数取得目标，并校验它位于可执行区域，`status="direct"`、`target_source="machine"`。
- 间接调用/跳转在 CFGFast 给出内部目标或外部符号时记 `resolved`，否则记 `unresolved`。`resolved` 也可能只有外部符号而没有内部目标。
- 间接目标由 CFGFast 恢复时保留来源：命中跳转表记 `cfgfast-jump-table`，其余记 `cfgfast-indirect`；未恢复时保留 `unresolved`，不做猜测。
- 完整间接调用目标求解、指针运算和跨过程传播不属于 M2。

### 6.5 地址取用（AT）候选

AT 候选来源包括：

| `source` | 来源 |
| --- | --- |
| `instruction-immediate` | 非直接 CALL/JMP 指令操作数中的立即数 |
| `instruction-address` | 可恢复的 LEA 地址（RIP/EIP 相对或无基址/变址的绝对位移） |
| `global-initializer` | 全局初始区域中按机器字对齐读取的值 |

只有命中已恢复函数入口的候选才写入对应函数的 `at_evidence`。普通直接 CALL/JMP 的目的地本身不算 AT 证据，即使它也是函数入口。

AT 候选是“可能被取地址”的线索，不是入口可达性证明，也不是完整指针分析结论。当前实现可能把恰好等于函数入口的常量误收为候选；也会漏掉复杂地址运算、运行时写入、未对齐数据和跨过程传播形成的指针。`address_taken` 只表示存在候选证据。

| 样本 | 函数 | 块 | 边 | CALL | 机器间接 CALL | 未解析间接 CALL | AT 函数 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `test_64` | 31 | 65 | 75 | 12 | 4 | 3 | 3 |
| `test_32` | 31 | 70 | 85 | 17 | 5 | 5 | 2 |

这些总数包含启动代码、运行库辅助代码和 PLT，不只是源码中的 5 个函数。`main`、`add`、`subtract`、`apply`、`invoke` 均以 `elf-symbol` 识别，代码范围位于各自符号范围内。

与间接调用相关的细节：

- `test_64` 有 4 个机器间接 CALL：1 个解析到外部 `__libc_start_main`，3 个未解析；未解析者是 `apply`、`invoke` 和启动代码中的调用，其中前两者保存了续点。
- `test_32` 有 5 个机器间接 CALL，均未解析；`apply`、`invoke` 的调用保存了续点。
- `unresolved_transfers` 记录所有未解析的间接转移，因此 `test_64` 为 6 项（3 个调用 + 3 个跳转），`test_32` 也为 6 项（5 个调用 + 1 个跳转），与“未解析间接 CALL”计数不同。

上述结果仅来自两个固定的、带调试信息的非 PIE 小样本。M2 未运行 bzip2，也没有新增或重编译 C 程序。

## 8. 限制

- **不是完整 CFG/指针分析。** 间接调用目标未完整求解；`fake_return`、`cfgfast-return` 和 AT 候选都不能当作已证明的指针事实。
- **CFGFast 固有边界。** 代码发现依赖入口、符号和可执行区域；`detect_tail_calls=False`，尾调用可能表现为跳转；优化、手工汇编或数据嵌入代码可能造成漏块或错块。
- **AT 是启发式。** 只检查有限来源，依赖已恢复块和函数入口；复杂地址计算、运行时构造、非对齐数据和跨过程指针会漏检，也可能产生偶然命中的候选。
- **不支持范围。** 当前仅处理 M1 可加载的 AMD64/X86 小端 ELF；未验证大型程序、PIE、stripped、其他架构或异构重定位。M1 曾做过临时 PIE/stripped 加载检查，但不构成 M2 的验收。
- **无运行期信息。** 不执行程序，不包含动态加载、运行期全局变量值或真实库代码；`auto_load_libs=False`，外部目标只记录符号。
- **阶段边界。** 不生成 VEX facts、对象内存块、SSA 或最终指针分析；这些属于后续阶段。
- **统计依赖样本。** 文中的函数/块/边/调用数量只对应本次两个固定样本，不能外推为一般程序的规模或精度。

## 9. 复现命令

```bash
# 安装锁定依赖
uv sync --locked

# 直接执行 M1→M2
PYTHONPATH=src uv run --locked python -m bpa \
  tests/fixtures/binaries/test_64 --stage m2 -o outputs/test_64

# 复用已有 M1
PYTHONPATH=src uv run --locked python -m bpa \
  tests/fixtures/binaries/test_64 --stage m2 \
  --m1 outputs/test_64/m1/binary.json -o outputs/test_64

# 自动测试（不重新编译样本）
PYTHONPATH=src uv run --locked python -m unittest discover -s tests -v
```

M2 产物位于 `outputs/<样本名>/m2/`，`outputs/` 不纳入 Git。
